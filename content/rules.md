# 课程规则

> 这一页说明四件事：作业能不能讨论、代码能不能公开、实验环境怎么保证安全、哪些内容可以发布。
>
> INFRA 01 的协作规则参考 MIT 6.5840：https://pdos.csail.mit.edu/6.5840/general.html
>
> 这一页是中文摘要，不是法律意见；INFRA 01 以官方原文为准。INFRA 02/03 是本站原创实验，规则见下文。

## 协作

1. **自己写代码。** 你可以读论文、读文档、读别人的设计思路，但提交的代码要你自己写，你要能解释每一行。
2. **不看别人的答案。** 不看同学、往年学生、网上博客的 lab 代码；不把别人的实现改个名字当成自己的。
3. **不公开可直接复制的代码。** INFRA 01 的 lab 代码必须私有；INFRA 02/03 的实验代码可以私有保存，但不要把完整实现当成教程公开。
4. **AI 的使用。** 可以用 AI 解释报错、查文档、讨论设计；不要让 AI 代写你讲不清的代码。课程要的是你理解机制，不是提交一个能跑的仓库。
5. **理解并能解释。** 能不看代码讲清楚协议、失败模式和测试在测什么；这比“测试绿了”更重要。
6. **论文题自己写。** 可以讨论论文，但不要看别人的答案。

## 自学

- INFRA 01 是 MIT 校内课；外部学习者没有正式的提交入口。
- 你不需要提交：`make mr`、`make kvsrv1`、`make raft1` 等本地测试就是判分器。
- 自学版的“完成”是：测试通过 + 能解释 + 能回答 design questions。

## 实验安全

- 只在一次性的 Linux 或 WSL2 环境里做内核实验；先快照，做完重装。
- 不要在生产机、共享服务器、公司集群上做；不要挂载宿主目录或 Docker socket。
- 不要用真实 token、云凭证、生产数据库；用 fake tool、本地文件、临时数据库。
- 权限逃逸、网络扫描、DoS 测试只打自己的环境；不要扫校园网、公司网或云上邻居。
- 多 agent 实验要给每个 agent 独立的工作区、网络和预算。
- 失败要报告：写清楚哪里失败、为什么、还有什么没解决；不要用假成功掩盖。

## 可以发布什么

**可以：**

- 概念笔记、论文摘要、架构图。
- 调试思路、常见 bug 清单、失败复盘。
- 自己的学习计划、时间记录。
- 对课程内容的**原创中文导读**（本站就是）。
- INFRA 02/03 的实验规格、设计图、故障报告（不含可直接复制的完整实现）。

**不可以：**

- INFRA 01 的 lab 代码、代码片段、可直接提交的解答。
- 课程讲义/论文的逐字翻译或大段复制。
- 别人的 lab 代码、往年答案。
- 用 AI 生成的、你自己讲不清的代码。
- 真实凭证、生产数据、别人的隐私。

## 检查清单

开始前：

- [ ] 我在一次性的 Linux/WSL2 环境里，已经做了快照。
- [ ] 我没有挂载宿主目录、Docker socket、云凭证。
- [ ] 我没有把真实 token 放进环境变量或命令行。
- [ ] 我知道怎么重装这个环境。

做完后：

- [ ] INFRA 01：`make ...` 全绿；INFRA 02/03：验收标准逐条通过。
- [ ] 我能不看代码讲清楚协议/机制和失败模式。
- [ ] 我能解释每个测试在测什么。
- [ ] 我写了 300 字：如果换一个系统，这个机制会怎样。
- [ ] 我没有把可直接复制的答案公开。
- [ ] 我清理了 cgroup、namespace、mount、iptables 规则和临时凭证。

## 为什么有这些规则

- 这些课的价值在“你能解释为什么”，不在“仓库能跑”。
- 并发、容器、内核实验的 bug 大多在边界条件和失败路径；自己调试过，才知道怎么讲。
- Agent OS 是探索方向，很多问题没有标准答案；能说清楚设计取舍和失败语义，比背一个框架更有用。
